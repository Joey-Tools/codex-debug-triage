# iCloud Eviction Reconstruction Protocol

Use this protocol for a small, explicitly authorized set of iCloud Drive files that remain resident after an eviction failure. It describes a guarded reconstruction, not a general repair script. Treat cloud deletion, local deletion, and replacement of a canonical file as separate decisions. Do not automate cleanup by deleting data on a best-effort basis.

## 1. Establish the failure and scope

1. Record the macOS version/build, exact error domains/codes, relevant provider messages, and the selected file's current metadata in a scoped local audit. Anonymize paths, cloud identifiers, per-file hashes, process IDs, and raw logs before publishing a public case note.
2. Establish whether the object is uploaded, unpinned, conflict-free, and still resident. A metadata/eviction error is not proof that file contents are corrupt.
3. Define the protected properties for this operation:
   - **Object identity:** device and inode for a local object; provider cloud ID for its cloud object.
   - **Content stability:** complete SHA-256 and byte length, produced only after effective write exclusion is established. Size/time are change signals, not protection against a writer that restores metadata.
   - **Access policy and metadata:** inventory ACLs, resource forks, Finder tags, non-provider extended attributes, and other metadata before reconstruction. Owner/group/mode describe access only when inspection confirms there is no extended ACL.
4. Check existing session authorization for the exact file list, identity-changing reconstruction, and deletion of old cloud objects/backups. Explain the effect on links/history and request only missing scope; do not ask again when those operations are already approved. Authorization does not extend beyond the approved manifest or to unapproved deletion.

Reject reconstruction by default if an extended ACL, resource fork, Finder tag, or any non-provider or unclassified metadata exists, until a metadata-aware preservation method has been separately verified. Do not blindly copy all xattrs: provider-private metadata must not be copied, and unknown metadata is not safe to discard. Do not interpret ctime, file flags, or directory child-entry changes as content mutation, or manually remove provider xattrs/change flags to force eviction. Device/inode, content hash, change signals, and access policy answer different questions.

## 2. Preserve and construct a fresh provider object

1. Create a complete raw backup outside every iCloud/File Provider-managed directory. Use a task-private `0700` directory under a verified parent chain; trust root/current UID, and reject ACLs granting other principals read, write, delete, or add-entry access. Ancestors must not let other principals replace entries; a traditional-mode writable sticky ancestor such as `/tmp` is acceptable only with an owned private leaf and safe ACLs. Bind/revalidate parent-chain and leaf identity. Create the raw file exclusively with `O_EXCL`, no-follow, mode `0600`, and current-UID ownership; never overwrite. A provider-managed copy is not an independent backup. Keep this raw backup until cleanup is safe.
   Establish source write exclusion for the baseline copy. Open the source without following symlinks, require a regular file with `st_nlink == 1`, bind descriptor/path identity, and revalidate type, link count, identity, byte length, and modification time before/after reading. Verify the complete source and raw SHA-256/length match and retain that receipt. An unverified or concurrently changing source blocks reconstruction; size/mtime checks alone do not exclude a writer that restores metadata.
2. Create a byte-for-byte copy from the verified raw backup under a fresh name in the same folder so the provider assigns a new cloud ID. Check and bind the destination parent chain, revalidating it before creation; its traditional permissions and ACLs must prevent untrusted principals from adding, deleting, writing, or replacing entries. Create the initial destination with `O_CREAT|O_EXCL|O_NOFOLLOW`, mode `0600`, and current-UID ownership. Before writing bytes, inspect the new object's ACL; reject any extended ACL or grant to other principals for read, write, delete, or add-entry access (`0600` alone does not rule out ACL grants). Bind its device/inode as the publisher-created identity; verify regular-file type and mode/owner, then revalidate descriptor/path identity while copying. If the name already exists, an ACL/access check fails, or exclusive creation fails, retain existing objects and stop; never overwrite. Do not rename or rewrite the failed provider object to simulate a new object, and do not copy its provider-private metadata.
3. Restore birth time, modification time, UID, GID, and mode only for the accepted no-ACL, no-unclassified-metadata scope. Never hard-code a UID, path, or inode from another run.
4. Wait for the fresh cloud object to report uploaded, idle, unpinned, and error-free. Confirm it has a new cloud ID. Evict it and verify that it becomes dataless/cold.
5. If any state is ambiguous, preserve both copies and stop. A fresh name by itself does not establish a successful upload or safe replacement.

## 3. Replace the canonical name with a rollback point

1. Under effective write exclusion, revalidate that the old canonical and fresh object are regular files with `st_nlink == 1`; this selects single-link topology, so unrelated link-count changes are not content-mutation evidence. Verify that the old canonical still matches the baseline raw receipt's complete SHA-256 and length, and that the fresh object matches that receipt's complete SHA-256 and length. Hashing the cold fresh object hydrates it: evict it again, confirm uploaded/idle/error-free/dataless state, and revalidate its identity, cloud ID, regular-file type, `st_nlink == 1`, length, dates, and applicable access policy against the fresh-hash receipt. Maintain exclusion, identity, regular-file type, and single-link topology through these checks and the coordinated moves of the old canonical to a held name and the fresh object to the canonical name. Both moves must use native coordinated no-replace operations with atomic destination-exists failure; a prior existence check is insufficient. If either destination exists, any check fails, or exclusion cannot be maintained, preserve all copies and stop before promotion. Moving the fresh object preserves its new provider identity.
2. Roll back only if the canonical path is absent and the held object still matches the recorded identity and complete SHA-256 under effective write exclusion. Use a native coordinated no-replace move for rollback; destination existence must fail atomically, since a prior absence check cannot prevent a race. If either check fails or the destination exists, stop and preserve all available objects for manual recovery.
3. Confirm the new canonical object is dataless. Establish effective write exclusion before reading the entire file from iCloud and hashing it against the raw backup; maintain exclusion through final eviction and cleanup. Wait until the provider reports the downloaded object resident and idle; allow up to 120 seconds for settling, then stop if it remains unsettled.
4. Evict the canonical object again. Revalidate device/inode, cloud ID, byte length, modification time, birth time, and applicable access policy against the cloud-hash receipt. `NSFileCoordinator` coordinates cooperating clients; it cannot prevent arbitrary POSIX, remote, or provider writes. An empty `lsof` result does not prove exclusion. Writable/update or unknown handles block cleanup, but absence of handles alone is insufficient. Do not re-read cold content just to recheck a digest, since that can rehydrate it; if a new hash is required, repeat the hash and final-eviction checkpoint.

## 4. Delete only after revalidation

Every deletion is fail-closed. Use native coordinated deletion and require the relevant authorization. Before deleting the held old object, recheck its identity and hash while effective write exclusion remains in force. Before deleting the raw backup, recheck its identity/hash and the canonical object's healthy uploaded/evicted state and receipt metadata/cloud identity, with the same exclusion still effective. Metadata/cloud identity and no open handles do not prove content stability after a hash. If continuous exclusion cannot be established, retain at least one verified independent local backup, report cleanup incomplete, and never delete the last known-good copy. Any read/revalidation error, missing path, identity mismatch, hash mismatch, or policy mismatch stops cleanup; do not collapse these outcomes into “missing” or retry blindly.

Never run a script that automatically removes old provider objects or backups after a timeout or partial success. Preserve evidence and copies on interruption. Report which individual checks passed and which deletion, if any, was actually completed.

## 5. Bound retries, time, and storage

- A provider may replace a local inode while materializing the same cloud object. An `ETIMEDOUT` (`Errno 60`) or `itemContentVersionMismatch(expected, received)` followed by a new inode is not permission to accept it automatically. Retain the previous object and raw backup; explicitly revalidate the new device/inode, cloud ID, UID/GID/mode, size, birth time, and modification time, then rerun the full content hash. After a bounded retry, stop rather than loop indefinitely.
- A timeout is effective only while its parent supervisor remains alive. On interruption, send SIGINT as designed, terminate and reap the child process group, and verify no child remains before reporting the operation stopped.
- Account dynamically for raw backup, fresh copy, hydration, and provider temporary copies; their peak can exceed a simple two-copy estimate. Maintain a changing free-space reserve and stop before starting an operation that would cross it. Bind progress records to source identity, operation ID, and timestamp: a progress JSON emitted before the first blocking read may still describe the previous source.
- Distinguish filesystem free space from Foundation's `importantUsage` estimate, which may include reclaimable caches. A Time Machine “purgeable” count is observational only unless separate cleanup is authorized. File-allocation deltas do not equal volume-free-space deltas, and snapshot counts do not measure reclaimable bytes.

## 6. Evidence boundaries

Do not restart all iCloud/File Provider services as a default action, weaken SIP, or attempt privileged debugger attachment to Apple daemons. Prefer the minimum user-authorized action. A trace without a target file descriptor or command argument cannot attribute the failing operation to a particular file or request. Keep root cause marked unknown unless evidence establishes it.
