# Case: iCloud Drive Eviction Repair, 2026-10-17

## Environment and symptom

- macOS 26.3, build 25D125.
- Twenty-two older Sony files were uploaded, unpinned, and had no known conflicts, but eviction failed with `NSFileProviderErrorDomain` code `-2008`, `NSPOSIXErrorDomain` code `1` (`EPERM`), and `libfssync.VFSFileError 22` at `cannotSetMetadata` with `FPFSSetMetadataFlags` raw value `134217728`.
- The observed flags included `0x40` (`UF_TRACKED`); the decmpfs value was a valid 36-byte `DATALESS_CMPFS_TYPE` (`0x80000001`). Neither was evidence of content corruption. Manually deleting xattrs or changing flags was not justified.

## Actions and result

- Restarting current-user `bird`, `fileproviderd`, the iCloud extension, `cloudd`, and `nsurlsessiond` did not fix the old objects. LLDB attachment to Apple daemons was denied while SIP remained enabled; SIP was not weakened.
- An `ffsctl` trace returned `EPERM` but contained no target FD or command argument that identified the file/request. The cause of the original metadata failure remains unknown.
- Rewriting the old provider object retained the failure. A complete byte-copy under a new name in the same folder received a fresh cloud ID and succeeded. The fresh object did not inherit old provider-private metadata; birth time, mtime, UID, GID, and mode were restored.
- The fresh object reached uploaded/idle/unpinned/error-free state, evicted successfully, was coordinated into the canonical name while preserving the new cloud ID, then hydrated and verified against the complete raw-backup SHA-256. After provider settling, it was evicted again and revalidated. Old held objects and raw backups were removed only after identity and full-hash checks.
- A 20-file batch plus the earlier two samples finished dataless with zero allocated bytes. All 20 cloud reads matched their expected SHA-256. The 20 originals' allocated size fell by 42,291,404,800 bytes (39.387 GiB); cleanup of old copies and raw backups completed.

## Limits and operational lessons

- One 18,018,936,432-byte file timed out on its first attempt after 20 minutes, then completed fully in about four minutes on a second attempt. This shows an 18 GB object was not inherently blocked by eviction size; it does not establish that all large files or future operations will succeed.
- For two observed materialization attempts, provider logs showed `itemContentVersionMismatch(expected, received)` and later successful fetches. Provider content-version changes alone do not establish why an inode changed, and these events do not explain the earlier `cannotSetMetadata`/`EPERM` failure.
- Space accounting must include simultaneous raw, fresh, hydrated, and provider-temporary copies. Final volume free space was about 30.8 GiB, while Foundation `importantUsage` estimated about 70.9 GiB and included potentially reclaimable cache. Ten Time Machine purgeable snapshots were observed but not manually removed. Allocation deltas were not treated as free-space deltas.
- Root cause remains unknown. The result supports a bounded fresh-cloud-object reconstruction for the verified files only; it is not proof that the same procedure will repair every eviction failure.
